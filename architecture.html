ontolayer · architecture

How it works

A filesystem-first, agent-editable ontology framework you run as a service. The ontology is a folder of markdown files (the source of truth); a backing store is a derived, queryable index. Agents read it, edit it, act through it, and grow it — every write goes through one validated, versioned path.

02The ontology is a folder

  types/       Order.md  Agent.md  Task.md ...
  actions/     issue_refund.md  assign_task.md ...
  connections/ crm-db.md  slack.md          # named sources
  connectors/  slack-threads.md ...          # ingest logic
  pipelines/   slack-ingest.md ...           # composed flows
  data/                                       # SOURCE OF TRUTH
    Order/  1042.yaml
    Task/   task-001.yaml
  .ontology/   data.db                        # derived index (gitignored)

Definitions vs data vs secrets

Definitions (types/actions/…) → git. The shared, reviewable meaning.

Instance data (data/*.yaml) → git + materialized into the store. Files are the source of truth.

The index (.ontology/data.db or Postgres) → derived, queryable, gitignored.

Secrets → env only (ONTOLAYER_STORE_*, ONTOLAYER_CONN_*), never committed.

03Key flows

Write — put / agent or file

  1. beforePut hooks enrich / derive fields
  2. validate types, constraints, state transitions
  3. store upsert (version + content hash)
  4. write back data/<Type>/<id>.yaml
  5. append oplog · afterPut hooks (embed / audit / notify)

Act — run_action

  1. validate typed inputs
  2. load target record (on: type)
  3. check preconditions + legal state transition
  4. apply effects as a put (no side effect unless valid)
  5. result returned; oplog records the change

Ingest — run_pipeline

  1. resolve connection (config + env secrets)
  2. connector pulls source → ctx.upsert
  3. transform maps / enriches (shared bag)
  4. each step writes through Dataset (validated)
  5. unknown concept → propose a new type

Sync — sync / materialize

  1. materialize: data/*.yaml → store on boot + on edit
  2. sync: pull peer's oplog since cursor
  3. apply (last-write-wins, hash no-op)
  4. advance cursor — idempotent, no echo
  5. git pull + materialize = distributed sync

04Individual vs shared (git model)

An ontology = a git repo

Individual agent = its own repo (private memory, local SQLite). Shared org = one canonical repo (Postgres, served over HTTP).

Read = overlay (own ∪ parents). Write to your own; propose_to a parent = git PR; everyone pulls merged truth.

Two run modes, one codebase

Local — ontology serve over stdio. One repo, offline, private.

Service — ontology serve --http. Many agents connect over the network to a shared ontology backed by Postgres + S3.

06Per-stack extension — where you build

Connection

A named source: kind + non-secret config; secrets from env. Reused by many connectors.

Connector

Ingest logic — sync(ctx). Register a kind or link a module:. ctx.upsert is validated.

Transform

Reusable map / enrich step over the shared context. Register or link per step.

Pipeline

Ordered connector + transform steps, threading a bag. A file per flow.

Hook

Middleware on every write — derive, embed, audit, notify. dataset.use() or config hooks:.

Adapter

New backend — implement Store / Blob. Same tools, no core change.

Per-stack recipe: a few connections + connectors + transforms, one pipeline file, maybe hooks, point stores:/blobs: at your backend. Core never forks. Share it all as a pack.
