ontolayer · data connectors

Ideas & Honest Critique

How do we guide people to build data connectors that work with the ontology? Every idea below is pitched, then genuinely criticized — most are not worth it. One is.

The constraint: a connector's job is simple — pull data from a source, map it to ontology objects, call ctx.upsert. The ontology validates; the store persists; files write back. The question is: what do we provide so people don't reinvent the same glue every time, without over-abstracting?

01Ideas

Not worth it

1. Visual connector builder (UI)

A web UI where you drag source fields onto object properties, configure auth, click "run." Low-code. Looks impressive in a demo.

Critique: We'd be building Airbyte. The UI is 10x the code of the connectors themselves. It targets non-developers — but our users are developers building agent systems. A YAML file + a 20-line JS module is faster for them than a point-and-click tool. And we'd have to maintain the UI across every source type. This is where projects go to die. Wrong audience, wrong cost.
Not worth it

2. Universal adapter layer (connect to "anything")

A generic adapter that auto-connects to any Postgres/MySQL/Mongo/API and auto-discovers the schema. "Point it at your DB and it just works."

Critique: This is the dream and the trap. Auto-discovery gives you table names and column types — not meaning. A column called cust_ref could be a customer ID, a string, or garbage. The whole point of the ontology is that a human decides what things mean. Auto-mapping skips the step that matters. You end up with a "semantic layer" that's just a renamed schema dump.

Even if it worked, every real DB has weird joins, soft deletes, JSON columns, views — the long tail of edge cases would eat us alive. Airbyte has 300+ connectors and thousands of contributors for a reason. We'd build a bad ETL tool instead of a good ontology framework.
Not worth it

3. Pre-built connectors for popular sources (Slack, GitHub, Notion, etc.)

Ship 10 connectors out of the box: Slack, GitHub, Notion, Salesforce, HubSpot, Linear, Google Docs, email, RSS, webhooks. "Batteries included."

Critique: Every SaaS API changes constantly. Auth flows differ. Rate limits differ. Pagination schemes differ. We'd be maintaining 10 API clients forever — that's an ops burden, not a framework feature. When Slack changes their API, our connector breaks, and the issue lands on us, not the user.

Worse: every company's Slack workspace maps differently to their ontology. One uses threads for tasks, another uses channels. A generic "Slack connector" either does too little (just dumps messages) or makes opinionated mapping decisions that are wrong for half the users.

The right move is to make writing a connector so easy that building your own takes 15 minutes, not 15 days. Ship zero connectors; make the connector so trivial nobody misses them.
Interesting but risky

4. LLM-generated connectors ("describe your source, get a connector")

The agent reads your object definitions + a description of your source, then writes the connector module for you. create_connector but the agent authors the sync() function.

Critique: This actually works for simple cases — an agent can write a 20-line fetch+map+upsert function if the source is a REST API with clear docs. But it fails silently on: auth flows (OAuth token refresh), pagination (cursor vs offset), rate limiting, error recovery, idempotency. The generated code looks right and breaks at 2am.

Also: it couples the connector to whatever the LLM guessed about the API. If the API changes, the agent has to regenerate, and now you're debugging AI-written code you don't understand.

Verdict: useful as a starting point ("scaffold me a connector for this API"), dangerous as a production solution. Could be a nice-to-have later, but not the core offering.
Has merit, limited scope

5. Mapping files (declarative source→object mapping, no code)

A YAML file that declares: source table/endpoint → object type, column → property, join → link. No code, just config. A generic runner reads the mapping and does the ETL.

# mappings/crm-to-customer.yaml
source:
  kind: postgres
  table: customers
  connection: crm-db
target: Customer
mapping:
  email: email_address
  name: full_name
sync: poll
interval: 5m
Critique: This works for the trivial case (flat table → flat object). Falls apart when: the source needs a JOIN, a computed field, a filter, conditional logic, or any transformation beyond column rename. Then you need an "escape hatch" — which is just... writing code. So the mapping file handles 60% of cases and the rest still need a code connector.

The mapping file IS a DSL, and DSLs always grow until they're a bad programming language.

Verdict: tempting but a trap. The 60% it handles are the easy 60% that are already trivial to write in code. The hard 40% is where people actually need help, and the mapping file can't help there.
Useful but secondary

6. Connector test harness ("does your connector actually work?")

A test runner that validates a connector against the ontology: run it in dry-run mode, check every upsert would pass validation, report type mismatches, missing required fields, bad link targets. ontology test-connector my-connector --dry-run.

Critique: Actually useful — the biggest pain with connectors is "it ran but silently produced garbage." A dry-run that catches mismatches before you commit data is real value.

But: our validation already runs on every ctx.upsert. A connector that produces bad data will get errors in the result right now. The test harness is just running the connector and collecting those errors — which is... run_connector against a test dataset. We almost have this.

Verdict: worth polishing (add --dry-run flag that validates without persisting), but it's a feature on the existing runner, not a new concept. Secondary to the main idea.
Interesting, premature

7. Connector marketplace / registry (share connectors as packages)

ontology add slack-connector — install a community connector from a registry. npm-style, but for ontology connectors.

Critique: Requires a community that doesn't exist yet. A marketplace with 3 connectors is worse than no marketplace — it signals "dead project." Building the registry infrastructure (publishing, versioning, discovery, trust) is a lot of work for zero users.

Also: a connector is a 20-line JS file. npm already exists. npm install @ontolayer/slack-connector and point module: at it. We don't need our own registry.

Verdict: the idea is right (ecosystem), the timing is wrong (no users yet). When there are 50 connectors in the wild, aggregate them. Don't build the marketplace before the market.
Overthinking it

8. CDC / real-time sync (stream changes from source DBs)

Use Postgres logical replication, Debezium, or change data capture to stream source changes into the ontology in real-time. Always fresh, no polling.

Critique: This is infrastructure, not ontology. Debezium exists. Postgres LISTEN/NOTIFY exists. If someone needs CDC, they pipe it into a connector's sync() — the connector is the integration point, not the framework. Building CDC into ontolayer means we're now maintaining a streaming pipeline engine.

Also: real-time is rarely needed for an ontology. Ontologies represent meaning and structure, not live event streams. A 5-minute poll is fine for 95% of use cases.

People who need CDC already have CDC. We just need to be easy to call from it.

02The winner

Build this

9. The Connector Guide: a spec + an example + a recipe, not a framework

Don't build connector infrastructure. Write the best documentation and example in the world so that writing a connector is a 15-minute copy-paste-edit job. The "product" is clarity, not code.

Why this wins:
Every other idea adds code, surface, and maintenance. This one adds understanding. The connector contract is already simple (sync(ctx) + ctx.upsert). What's missing is not tooling — it's a clear, copy-paste path from "I have a source" to "it's in my ontology."

The hardest part of building a connector is not the code — it's knowing what to do. Which fields map where? How do I handle auth? What about pagination? Idempotency? Error handling? A great guide answers every question before you have it.

What it actually is:

  1. A spec page (in the ontology folder or on a docs site) that documents the connector contract in full: what ctx gives you, what sync() returns, how errors propagate, how hooks apply, how files write back. The current spec mentions connectors in 3 sentences. This needs to be 2 pages with every edge case covered.
  2. A cookbook of annotated examples — not abstract, but real scenarios people actually face:
    • Pull from a REST API (with auth token from env, pagination, rate-limit backoff)
    • Pull from a Postgres table (with connection, incremental by timestamp)
    • Pull from a CSV/JSON file dropped in a folder
    • Pull from a webhook (connector called by an external trigger)
    • A transform that enriches records after ingest (e.g. resolve a foreign key, compute a derived field)
    Each example is a complete, runnable file. Copy it, change the URL/table/mapping, done.
  3. A recipe template — a single .mjs file with blanks to fill in: 
    // connectors/my-source.mjs — copy this, fill in the blanks
export default {
  async sync(ctx) {
    // 1. Connect to your source
    const token = ctx.env("MY_SOURCE_TOKEN");
    const res = await fetch("https://api.example.com/items", {
      headers: { Authorization: `Bearer ${token}` },
    });
    const items = await res.json();

    // 2. Map each item to an ontology object and upsert
    let ingested = 0;
    for (const item of items) {
      await ctx.upsert("MyObject", item.id, {
        name: item.title,
        status: item.state,
        // ... map your fields here
      });
      ingested++;
    }

    // 3. Return the result
    return { connector: "my-source", ingested, errors: [] };
  },
};
  4. A checklist — "before you ship your connector" — idempotency (upsert by stable ID), error handling (catch per-record, don't abort the batch), incremental sync (store a cursor in ctx.bag or the env), secrets (never hardcode, use ctx.env()).
  5. A dry-run flag on the existing runner — ontology run-connector my-source --dry-run — validates every upsert against the ontology without persisting. This is the only code worth adding.
Why this beats everything else:
  • Zero new abstractions. Zero new code to maintain (except dry-run, which is tiny).
  • Works for every source — REST, SQL, file, webhook, custom — because it's guidance, not a framework.
  • Scales with the community: when someone writes a great Slack connector, it becomes an example in the cookbook. The guide grows by accumulation, not by building infrastructure.
  • The ontology does the hard work (validation, transitions, file write-back, hooks). The connector just maps. Making the mapping obvious is the whole job.
  • Respects the boundary: structure is defined (the contract), movement is open (the implementation).

03Why nothing else is worth it (honest comparison)

What we'd be building

Visual builder → Airbyte competitor (wrong game)

Universal adapter → bad ETL tool (can't understand meaning)

Pre-built connectors → 10 API clients to maintain forever

Mapping DSL → a bad programming language that handles 60% of cases

CDC → infrastructure that already exists

Marketplace → registry for a community that doesn't exist

What we should build

A spec page that makes the contract crystal clear

5 annotated examples covering real scenarios

A copy-paste template with blanks

A checklist (idempotency, errors, incremental, secrets)

A --dry-run flag on the existing runner

Total new code: ~20 lines (dry-run). Total new docs: ~5 pages.

04The principle

The ontology framework's job is to validate and store. A connector's job is to map. The guide's job is to make the mapping obvious.

Don't build connector infrastructure. Build connector clarity. The contract is already right (sync(ctx) + ctx.upsert). What's missing is a guide so good that nobody needs to ask how.

The best connector framework is no framework — just a contract, a template, and a few great examples. Everything else is scope creep disguised as features.

05If we must add code (ranked)

  1. --dry-run on the runner — validate without persisting. ~20 lines. High value / zero risk.
  2. Incremental cursor helper — ctx.cursor.get(key) / ctx.cursor.set(key, val) backed by a small table. Connectors that poll need to remember "where they left off." Currently they'd use env vars or bag state (which doesn't persist between runs). This is the only real gap in the contract. ~50 lines.
  3. LLM-scaffold command — ontology generate-connector --source "Slack API" --object Message → the agent writes a starter .mjs file. Nice to have. Depends on an LLM being available, which is a big assumption for a framework. Later.

Everything else: not worth it.
