Product Requirements · v0.3 draft

Agent Ontology Layer

A plug-and-play ontology that lives as agent-editable text files, tracked by git, exposed to any agent framework over MCP. Agents don't just read it — they query it, act through it, and grow it. Open source, local-first.

Status — v0 built. Editable-files core: format, loader, validator, 11-tool MCP server, git-commit-per-edit, CLI (init / serve / validate), runnable e-commerce example. Runs on a laptop — no database, no cloud. The data layer and everything below plugs onto this seed.

01Problem

Agents are probabilistic. Pointed at raw tables they don't know what an entity means, can't follow relationships, and produce invalid results. Existing semantic layers (dbt, LookML) are built for SQL/humans and are read-only — an agent can't evolve them. We want an ontology agents can read, act through, and edit, that a person sets up in 60 seconds.

02Core idea

The ontology is a git-tracked folder of markdown files. Each file: a machine part (frontmatter — schema, constraints, store mapping) and a prose part (docs, examples). Text is the source of truth for meaning; a backing store holds the data. An MCP server wraps the folder for query, actions, and safe edits. Plain text → any agent can read it with no server running.

03Boundary — what it is / what it isn't

The most important scope decision: define a contract + ship one batteries-included default. Precise where portability demands it; open where variety lives.

The line: structure is defined, movement is open. Precise contract, open plumbing.

HOLD — defined & owned (the spine)

ontology file format (spec) Store + Blob interfaces config + resolver (store→adapter→env) reference backend: SQLite + FS + sqlite-vec get / traverse / search / run_action + validator MCP tool surface

LEAVE OPEN — interface + one example

extra backends (Postgres, S3, Snowflake…) ingest / connectors — tiny contract, not an ETL platform entity resolution / dedup — a hook, not a solution auth / multi-tenant / governance — org-mode

Too vague → nothing portable, no plug-and-play. Too much → Palantir + Airbyte scope death. The line is the interface.

04The four pieces

1 · Text ontology

Types, actions, connectors as markdown, git-tracked. Reversible, reviewable. Agent and human read the same files.

2 · Backing store

Postgres (rows) + S3 (blobs) for orgs; SQLite + FS by default. Joined to defs by the store: mapping.

3 · Actions

Text contract → real op. Validate types then constraints → execute. No side effect until validated.

4 · Connectors

Ingest email/Slack → map to types → upsert. Unknown concept → propose an ontology edit. Grows bottom-up.

Full format in spec/FORMAT.md.

06Agent-editable ontology

Edit tools (create_type, add_property, add_link, add_constraint, create_action, update_type_doc) patch the markdown and make a git commit. Text + versioned = safe (revert), reviewable (diff / PR), composable (connectors propose, a human approves). The ontology grows from data instead of being frozen up front.

07Scopes & server modes (the git model)

An ontology = a git repo. The atom. Individual agent = its own repo (private memory); shared org = one canonical repo; the relationship = git (remote + branch + PR) + read overlay.

Local mode (built)

ontology serve ./repo over stdio. One repo, local files + git. Private, fast, offline. The solo scope.

Org mode (planned)

One server holds many repos over HTTP, routed by id, gated by auth. A multiplexer over repos. The shared scope.

Hybrid is the norm: agent runs local (speed + private memory) with the org repo as a git remote + parent. Compose by overlay (read own ∪ parents, parents read-only, provenance tagged); track + promote by git (write your own; propose_to a parent = PR; everyone pulls the merged truth).

08Storage & config (the data layer)

Definitions → git. Data → the store. Secrets → env.
  • Committed (no secrets): named stores in ontology.config.yaml + per-type store: mapping (table, columns, join keys). Structural, shareable.
  • Not committed (secrets): URLs/keys via env (ONTOLAYER_STORE_<NAME>_<FIELD>) or a gitignored .env; ship .env.example.
  • Code: Store/Blob interfaces in core; adapters as optional packages (store-sqlite default, store-postgres, blob-fs default, blob-s3); a resolver binds store → adapter → env.
  • Local default: SQLite + FS + sqlite-vec → data works with zero config, offline. Org: point stores at Postgres/S3 via env; same mappings, same tools.

09Plug-and-play

npx ontolayer init my-ontology   # scaffold folder + example + git
ontology serve my-ontology       # start MCP endpoint → point your agent at it

MCP mode: point any MCP agent at serve. Files mode: a framework that reads a repo just reads ontology/ + a thin SDK.

11How an agent uses it

  1. Source data → search / get / traverse.
  2. Propose result/action → run_action.
  3. Validator checks: types (Pydantic), then constraints/inference (ontology).
  4. Valid → execute. Invalid → retry via LLM, or escalate to a human.
  5. New concept → edit_ontology / propose_to grows it; human approves.

12Example — e-commerce

The bundled init example catches, without hand-written English rules:

  • status = "probably shipped" → rejected (enum).
  • second refund on the same order → rejected (cardinality).
  • payout to a SupportRep instead of the buyer → rejected (disjoint).
  • support email mentions "chargeback" (unknown) → connector proposes a Chargeback type; human approves.
